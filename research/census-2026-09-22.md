# Stage 0 evidence — Pi 0.87.1 (2026-09-22)

Recorded with `scripts/probe-live.mts` against `@earendil-works/pi-coding-agent`
0.87.1 (local-prefix install, never global), Node 24.14.1, macOS arm64. The
terminal on the other side of the PTY was `@xterm/headless` (Agent Code's
emulator). Every run used a throwaway HOME / `PI_CODING_AGENT_DIR` / git
project under the OS temp directory and the scripted `faux` model
(`scripts/probe/faux.ts`), so no login, network or quota was involved.

18 scenarios, all completed without a probe timeout:
`plain tool abort error queued socket socket-idle-followup socket-abort
new-session tree fork resume compaction dialog trust user-bash paste kill`.
The findings below are pinned by `src/testing/fixtures.corpus.test.ts`, so a
re-recording against a later Pi that changes one of them fails there, naming
the design assumption.

**No real-provider recording.** At capture time this machine had no Pi login
(`~/.pi/agent/auth.json` was an empty `{}` left by the research run), so every
recording uses the faux model. Structure, write order and event order come
from real Pi code; content shapes that only real providers produce
(thinking signatures, redacted thinking, images, provider-specific error
text) are NOT covered. See "Open" below.

## Hypotheses (spec §8)

| # | Hypothesis | Verdict | Evidence |
|---|---|---|---|
| H1 | `--session-id <new uuid>` creates `<ts>_<uuid>.jsonl`; stderr warning harmless | **Holds** | File `…_<launched uuid>.jsonl`, header `id` = the uuid. Pi prints one line `Warning: No project session found with id '<id>'; creating a new session with that id.` above its banner, then renders normally. Nothing exists on disk until the first reply completes — even the assistant's own `message_end` sees `fileBytes: -1`. On exit Pi prints `To resume this session: pi --session <id>`. |
| H2 | `getSessionFile()` at `session_start` is the file later written | **Holds** | For `startup`, `new`, `fork`, `resume` every `session_start.sessionFile` is one of the recorded files and its header id equals `session_start.sessionId`. `session_shutdown{reason:new|fork|resume}` carries `targetSessionFile` (the next file) *before* the switch. |
| H3 | At the extension's `message_end` the row is on disk (doorbell) | **Refined — `message_end` is NOT a doorbell; `turn_end` and `agent_settled` are** | Pi's session writer subscribes after extension handlers: at `message_end` the file size is unchanged (user row appears by the assistant's `message_start`; assistant row by `turn_end`). At every `turn_end` with an existing file, `messageEntryId` and all `toolResultEntryIds` are fully on disk (checked on 30+ turn ends). At every `agent_settled`, the reported leaf is on disk. |
| H4 | `agent_settled` once per run, after the last row, not while queued prompts are pending | **Holds** | `agent_start`/`agent_settled` strictly alternate in every scenario. A steer and a follow-up queued during a run are delivered inside the same span (three assistant replies between one start/settle pair). An aborted or errored reply still ends in exactly one `agent_settled`. |
| H5 | `sendUserMessage` delivers; `followUp` while busy queues; idle starts a run | **Refined — a busy prompt WITHOUT `deliverAs` is silently lost** | `pi.sendUserMessage(text)` while busy returns normally and Pi fires `input{source:'extension'}` for it, but the message is never persisted: `prompt()` throws "Specify streamingBehavior" inside an un-awaited promise. With `deliverAs: 'followUp'` or `'steer'` it is persisted and delivered (steer first). `deliverAs: 'followUp'` while idle is ignored by Pi and starts a normal run. ⇒ the bridge always passes `followUp`, and neither `input` nor a clean return can serve as a delivery acknowledgement. |
| H6 | `/tree` → `session_tree` + new leaf; the last line is the active leaf | **Refined** | A move without a summary writes NOTHING: `session_tree.newLeafId` is an existing entry and the file's last row stays the old leaf until the next append (whose `parentId` is the new leaf). A move with a summary appends a `branch_summary` row that is the new leaf (parent = the target's parent when the target is a user message, whose text goes back to the editor). Pi itself resolves the leaf as the last row on load, so cold reads must too; live reads follow `session_tree.newLeafId`. |
| H7 | Project trust vs `-e` extensions | **Observed** | `project_trust{cwd}` reaches `-e` extensions ~300 ms before `session_start`; returning `{trusted:'undecided'}` leaves Pi's native selector (Trust / Trust parent / this session only / Do not trust …). It is NOT an extension `ui_prompt_start`. Declining lets Pi start with "This project is not trusted" and project resources ignored. ⇒ the bridge must connect from its `project_trust` handler to report the pending prompt. |
| H8 | The pane's terminal answers DA1 / Kitty queries | **Holds** | `@xterm/headless` answered every startup query; zero hand answers; startup ~300 ms to `session_start`. |
| H9 | A 0700 dir + socket under `/tmp` is reachable from pi | **Holds** | The recorder connected (extension → host) in every scenario. |
| H10 | v1/v2 files are pre-migration leftovers | **Partly open** | All recorded files are v3. Source (`session-manager.ts` `migrateToCurrentVersion`) shows Pi REWRITES an old file in place when it loads it, so resuming a v1/v2 session changes the file under a tailer (shrink/replace ⇒ reset). v1 rows have no `id`/`parentId` (a linear list); v2→v3 renames role `hookMessage` → `custom`. A hand-authored v1 excerpt modelled on Pi's own `test/fixtures/large-session.jsonl` covers the reader's tolerance. |

## Other findings

- **Write shape.** Every non-header row: `{type, id (8 hex), parentId, timestamp (ISO)}` plus its payload; the first three rows of a fresh file are always `session`, `model_change`, `thinking_level_change`, then a `system` message, then the first `user` message.
- **Aborted reply** (Esc or `ctx.abort()`): assistant row with `stopReason:'aborted'`, `errorMessage:'Operation aborted'` and the partial content streamed so far (thinking + partial text).
- **Provider error:** assistant row `content: []`, `stopReason:'error'`, `errorMessage`; the run settles; the next prompt works.
- **Killed process mid-stream:** the user row is persisted, the partial assistant never is.
- **Fork** writes the new file immediately (not lazily), copying the ancestor entries **with their original ids**, header `parentSession: <parent file path>`. `/new` files are lazy (first reply), uuidv7 ids.
- **Resume by relaunch:** `pi --session-id <existing id>` reopens the file (`session_start{reason:'startup'}` with `fileBytes > 0`) and appends.
- **Compaction** (`/compact`): `session_before_compact` → `session_compact{compactionEntry}`; row `{type:'compaction', summary, firstKeptEntryId, tokensBefore, details, usage, systemMessage?}` whose `parentId` is the old leaf and whose `firstKeptEntryId` points BACK to an earlier entry. With a too-small session Pi emits `session_compact_failed{errorMessage:'Compaction failed: Nothing to compact (session too small)'}`.
- **User `!cmd`:** `user_bash` event, row role `bashExecution {command, output, exitCode, cancelled, truncated, excludeFromContext}`; not a run (no `agent_start`).
- **Bracketed paste** of 30 lines + Enter is delivered as one user message.
- **Extension dialog:** `ui_prompt_start{kind:'confirm', title}` → `ui_prompt_end`; the dialog renders inline above the editor ("↑↓ navigate enter select escape/ctrl+c cancel").
- **`input` event** fires for every prompt, with `source: 'interactive' | 'extension'` and `streamingBehavior` (absent when idle).

## Design consequences (applied to the spec in the same commit)

1. Doorbell = `turn_end` (with its entry ids), `agent_settled`, `session_tree`, `session_compact`, `session_start`. `message_end` is forwarded only as a phase hint.
2. The bridge always sends `deliverAs: 'followUp'`. Acknowledgement = Pi's own evidence that the text entered the conversation or the queue: a user `message_start` whose text equals ours, or `hasPendingMessages()` turning true after our `input` event. Otherwise the outcome is `unknown`, never `ok`.
3. Live leaf = `session_tree.newLeafId`; cold leaf = last row. A move without a new row is a pure live-state change (history reset + re-projection from the in-memory tree).
4. The bridge connects from `project_trust` as well as `session_start`, and reports `trust-pending` until `session_start`.
5. The durable reader treats a size shrink / inode change as a rewrite (migration) and emits a reset.
